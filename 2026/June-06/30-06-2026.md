## Part 1 — The IDOR Vulnerability (Insecure Direct Object Reference)

#### What was happening

The `/emr/profile/<patient_id>` and `/emr/prescriptions/<patient_id>` endpoints
required a valid JWT (any role) but did not check *who* the caller was relative
to the resource:

```python
# Before — only JWT validation, no ownership check
@emr_bp.route("/profile/<patient_id>")
@_require_jwt()
def get_profile(patient_id):
    pid = _resolve_pid(patient_id)
    row = db.execute("SELECT * FROM patient_profiles WHERE patient_id=:pid", {"pid": pid})
    return jsonify(dict(row))
    # Any authenticated user (any doctor, any patient) could read any record!
```

This is a textbook IDOR — the object reference (`patient_id`) is directly accessible
without verifying that the caller is *authorized* to access it.

#### Impact

- Doctor A could read Doctor B's patients' records with no access grant
- Patient A could read Patient B's records
- An attacker with any valid JWT (even a patient account) could enumerate all records

## Part 2 — Fix: `_caller_may_access_patient()`

```python
# server/server.py

def _caller_may_access_patient(patient_id: str) -> bool:
    """
    Returns True if the current JWT caller is allowed to access patient_id's data.

    Rules:
      - Role = patient  → may only access their own record (uid == patient_id)
      - Role = doctor   → must have an active (non-expired) approved access record
    """
    payload    = request.jwt_payload
    caller_id  = payload["uid"]
    role       = payload["role"]

    if role == "patient":
        return caller_id == patient_id

    if role == "doctor":
        row = db.execute("""
            SELECT 1
            FROM access_requests ar
            JOIN wrapped_keys wk ON wk.request_id = ar.request_id
            WHERE ar.doctor_id  = :did
              AND ar.patient_id = :pid
              AND ar.status     = 'approved'
              AND wk.expires_at > NOW()
            LIMIT 1
        """, {"did": caller_id, "pid": patient_id}).fetchone()
        return row is not None

    return False   # unknown role → deny

# Applied at every patient-scoped endpoint
@emr_bp.route("/profile/<patient_id>")
@_require_jwt()
def get_profile(patient_id):
    pid = _resolve_pid(patient_id)
    if not _caller_may_access_patient(pid):
        return jsonify({"error": "access_denied"}), 403
    row = db.execute("SELECT * FROM patient_profiles WHERE patient_id=:pid", {"pid": pid})
    return jsonify(dict(row))
```

Applied to all 6 patient-scoped endpoints: `profile`, `prescriptions`, `lab_reports`,
`conditions`, `encounters`, and `wrapped_key`.

## Part 3 — The Expiry Check in Detail

The SQL query is worth understanding carefully:

```sql
SELECT 1
FROM access_requests ar
JOIN wrapped_keys wk ON wk.request_id = ar.request_id
WHERE ar.doctor_id  = :did       -- this specific doctor
  AND ar.patient_id = :pid       -- accessing this specific patient
  AND ar.status     = 'approved' -- request was approved (not pending/denied)
  AND wk.expires_at > NOW()      -- the granted key has not yet expired
LIMIT 1
```

The JOIN on `wrapped_keys` is critical — `access_requests.status = 'approved'`
alone is not enough because the wrapped key has its own `expires_at`. A doctor could
have `status = 'approved'` in `access_requests` but an expired key in `wrapped_keys`.
Without the JOIN, they'd still get data after the key expired.

#### Why `LIMIT 1`?

A patient could grant access to the same doctor multiple times (e.g. a 24h grant
that expired, then a new grant). `LIMIT 1` makes the check O(1) regardless of how
many historical grants exist.

## Part 4 — Wrapped Key Endpoint Guard

The `/emr/wrapped_key/<patient_id>` endpoint needed the same treatment:

```python
@emr_bp.route("/wrapped_key/<patient_id>")
@_require_jwt(roles=["doctor"])
def get_wrapped_key(patient_id):
    pid       = _resolve_pid(patient_id)
    doctor_id = request.jwt_payload["uid"]

    if not _caller_may_access_patient(pid):
        return jsonify({"error": "access_denied"}), 403

    # Return the most recent active wrapped key for this doctor
    row = db.execute("""
        SELECT wk.wrapped_key, wk.expires_at
        FROM wrapped_keys wk
        JOIN access_requests ar ON ar.request_id = wk.request_id
        WHERE ar.doctor_id  = :did
          AND ar.patient_id = :pid
          AND ar.status     = 'approved'
          AND wk.expires_at > NOW()
        ORDER BY wk.expires_at DESC
        LIMIT 1
    """, {"did": doctor_id, "pid": pid}).fetchone()

    if not row:
        return jsonify({"error": "no_active_key"}), 404

    return jsonify({"wrapped_key": row["wrapped_key"], "expires_at": row["expires_at"].isoformat()})
```

The `ORDER BY wk.expires_at DESC LIMIT 1` selects the most recent active key —
solving the bug where the wrong wrapped key was being returned when a patient had
granted access multiple times (the original June 28 bug).

## Part 5 — Status Transition Validation

The `PATCH /api/access/request/<id>/status` endpoint previously allowed setting
any arbitrary status string:

```python
# Before — no validation
db.execute("UPDATE access_requests SET status=:s WHERE ...", {"s": body["status"]})
```

Added an allowlist:

```python
ALLOWED_STATUSES = {"denied", "expired", "cancelled"}
# Note: "approved" is NOT here — approval goes through /approve_request which also writes a wrapped key

def update_request_status():
    new_status = body.get("status", "")
    if new_status not in ALLOWED_STATUSES:
        if new_status == "approved":
            return jsonify({
                "error": "use_approve_endpoint",
                "hint": "POST /api/access/approve to approve a request"
            }), 400
        return jsonify({"error": "invalid_status", "allowed": list(ALLOWED_STATUSES)}), 400
    ...
```

## Questions I Still Have

- Should `_caller_may_access_patient()` be a decorator instead of a function call? A decorator would make it harder to accidentally skip — `@_require_patient_access` would be more explicit than a manual `if not _caller_may_access_patient(pid): return 403`.
- The `expires_at > NOW()` check uses database server time. If the app server and DB server clocks are skewed, a key might appear active on one and expired on the other. Should there be a clock-sync health check at startup?
- Should a patient be notified (email / in-app alert) when a doctor accesses their record? This would close the audit visibility loop for patients.
