## Part 1 — Decentralised vs. Centralised: What It Actually Means Here

In a traditional hospital system, the server stores plaintext records and controls access
via role-based permissions. MedVault inverts this:

| Concern | Traditional | MedVault |
|---|---|---|
| **Who stores data?** | Server (plaintext) | Client (encrypted) |
| **Who holds the key?** | Server / DBA | Patient (private key, OS-protected) |
| **How does a doctor read?** | Server checks role → returns data | Patient grants wrapped AES key → doctor decrypts locally |
| **What does the server see?** | Plaintext records | Ciphertext + encrypted key blobs only |
| **Access expiry** | Admin revokes role | Wrapped key has TTL; server refuses to serve after expiry |

The phrase "server-side zero access to plaintext" means the server never has the AES key
to decrypt a record — even a compromised server returns only useless ciphertext.

## Part 2 — The Hybrid Cryptography Stack (RSA + AES)

#### Why Hybrid?

RSA can only encrypt data up to `(key_size / 8) - padding` bytes. A 4096-bit RSA key
can encrypt ~446 bytes — far too small for a full medical record. So:

- **AES-256-GCM** encrypts the actual patient data (fast, handles arbitrary length)
- **RSA-OAEP** encrypts the AES key (called "key wrapping")

The server stores: `{ ciphertext: AES(record), wrapped_key: RSA_pub(aes_key) }`

#### Key Generation Flow

```
Patient registers:
  1. generate_rsa_keypair(key_size=4096)          → (pub_key, priv_key)
  2. Store pub_key on server (users table)
  3. Store priv_key locally via DPAPI / AES-GCM   ← OS-backed, never leaves device
  4. Generate AES-256 key                         → aes_key
  5. AES-GCM encrypt medical record              → ciphertext
  6. RSA-OAEP encrypt aes_key with own pub_key   → self_wrapped_key
  7. Upload { ciphertext, self_wrapped_key }      → server stores encrypted blob
```

#### Doctor Access Grant Flow

```
Patient grants access to doctor D:
  1. Patient fetches D's public key from server
  2. Patient decrypts own aes_key using own private key
  3. Patient re-wraps aes_key with D's public key   → doctor_wrapped_key
  4. Patient POSTs { doctor_id, doctor_wrapped_key, expires_at } to server
  5. Server stores wrapped key with TTL
  6. Doctor fetches ciphertext + their wrapped_key
  7. Doctor decrypts wrapped_key with their private key → aes_key
  8. Doctor decrypts ciphertext with aes_key → plaintext record
```

At no point does the server see the AES key or plaintext. The patient's private key
never leaves their device.

## Part 3 — Access Control State Machine

Mapped out all valid states for a doctor access request:

```
                    ┌──────────┐
                    │ PENDING  │  ← Doctor sends request
                    └────┬─────┘
              ┌──────────┴──────────┐
              ▼                     ▼
        ┌──────────┐         ┌───────────┐
        │ APPROVED │         │  DENIED   │  (terminal)
        └────┬─────┘         └───────────┘
             │
    (TTL expires after 24h)
             │
             ▼
        ┌──────────┐
        │ EXPIRED  │  (terminal — server enforces, not just UI)
        └──────────┘
             │
    (doctor re-requests)
             │
             ▼
        ┌──────────┐
        │ PENDING  │  ← Back to start
        └──────────┘
```

Key insight discovered today: the "EXPIRED" state must be enforced **server-side**,
not just in the UI. A doctor could call the API directly with a valid JWT and bypass
any frontend TTL display. The server must check `expires_at` on every data read — 
which the June 30 commit will enforce properly.

## Part 4 — Database Schema (Current State)

```sql
-- Core tables as they stand after yesterday's work

CREATE TABLE users (
    user_id     UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    username    TEXT UNIQUE NOT NULL,
    name        TEXT NOT NULL,
    email       TEXT UNIQUE NOT NULL,
    pw_hash     TEXT NOT NULL,          -- werkzeug pbkdf2:sha256
    role        TEXT CHECK (role IN ('patient', 'doctor')),
    public_key  TEXT,                   -- RSA public key (PEM)
    created_at  TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE patient_profiles (
    patient_id      UUID REFERENCES users(user_id) PRIMARY KEY,
    dob             DATE,
    blood_type      TEXT,
    allergies       TEXT,               -- comma-separated, normalised on write
    emergency_contact TEXT,
    completeness_pct INTEGER DEFAULT 0
);

CREATE TABLE access_requests (
    request_id   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    patient_id   UUID REFERENCES users(user_id),
    doctor_id    UUID REFERENCES users(user_id),
    status       TEXT DEFAULT 'pending', -- pending | approved | denied | expired
    requested_at TIMESTAMPTZ DEFAULT NOW(),
    responded_at TIMESTAMPTZ
);

CREATE TABLE wrapped_keys (
    key_id       UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    request_id   UUID REFERENCES access_requests(request_id),
    patient_id   UUID REFERENCES users(user_id),
    doctor_id    UUID REFERENCES users(user_id),
    wrapped_key  TEXT NOT NULL,         -- RSA-OAEP encrypted AES key (base64)
    expires_at   TIMESTAMPTZ NOT NULL
);
```

## Questions I Still Have

- If a patient loses their private key (device wipe, OS reinstall) — how do they recover access to their own records? Is there a key escrow mechanism, or are records permanently inaccessible?
- Should `expires_at` be extended by the patient, or should the doctor always have to re-request? Auto-extend feels like a security risk.
- The `wrapped_keys` table grows unbounded — does it need a cleanup job to delete expired entries older than N days?
