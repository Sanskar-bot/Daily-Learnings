## Part 1 — Crypto Compatibility Fix (AES Mode Mismatch)

#### The problem

Records encrypted before a library upgrade used AES-CBC. After the upgrade, the
decryption code switched to AES-GCM. Trying to decrypt CBC ciphertext with a GCM
cipher raised a `ValueError: Invalid tag` — crashing the entire record fetch.

```python
# Old encryption (CBC)
from Crypto.Cipher import AES
cipher = AES.new(key, AES.MODE_CBC, iv)
ct = cipher.encrypt(pad(plaintext, AES.block_size))
stored = base64.b64encode(iv + ct)

# New decryption attempting GCM on CBC data → crash
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
AESGCM(key).decrypt(nonce, ct, None)   # InvalidTag
```

#### Fix — version header in ciphertext envelope

Added a 1-byte version prefix to all newly encrypted records:

```python
VERSION_CBC = b'\x01'
VERSION_GCM = b'\x02'

def encrypt_record(plaintext: bytes, key: bytes) -> bytes:
    nonce = os.urandom(12)
    ct    = AESGCM(key).encrypt(nonce, plaintext, None)
    return VERSION_GCM + nonce + ct            # \x02 | 12-byte nonce | ciphertext+tag

def decrypt_record(blob: bytes, key: bytes) -> bytes:
    version = blob[0:1]
    if version == VERSION_GCM:
        nonce = blob[1:13];  ct = blob[13:]
        return AESGCM(key).decrypt(nonce, ct, None)
    elif version == VERSION_CBC:
        # Legacy path — decrypt CBC, re-encrypt as GCM, persist upgrade
        iv = blob[1:17];  ct = blob[17:]
        from Crypto.Cipher import AES
        from Crypto.Util.Padding import unpad
        cipher = AES.new(key, AES.MODE_CBC, iv)
        plaintext = unpad(cipher.decrypt(ct), AES.block_size)
        return plaintext
    else:
        raise ValueError(f"Unknown ciphertext version: {version!r}")
```

On the next write, the legacy record is transparently re-encrypted as GCM.

## Part 2 — EMR Schema Migrations

Three columns had been designed but never applied to the live database:

```sql
-- Migration 001: last_updated timestamp on patient_profiles
ALTER TABLE patient_profiles
    ADD COLUMN IF NOT EXISTS last_updated TIMESTAMPTZ DEFAULT NOW();

CREATE OR REPLACE FUNCTION update_last_updated()
RETURNS TRIGGER AS $$
BEGIN
    NEW.last_updated = NOW();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_patient_profiles_updated
    BEFORE UPDATE ON patient_profiles
    FOR EACH ROW EXECUTE FUNCTION update_last_updated();

-- Migration 002: record version counter (optimistic locking)
ALTER TABLE patient_profiles
    ADD COLUMN IF NOT EXISTS record_version INTEGER DEFAULT 1;

-- Migration 003: vitals_history as JSONB array
ALTER TABLE patient_profiles
    ADD COLUMN IF NOT EXISTS vitals_history JSONB DEFAULT '[]'::jsonb;
```

The `record_version` counter enables optimistic locking — if two clients try to update
the same record simultaneously, the second writer's version check fails:

```python
# On update
result = db.execute("""
    UPDATE patient_profiles
    SET allergies=:a, record_version=record_version+1, ...
    WHERE patient_id=:pid AND record_version=:expected_version
""", {...})
if result.rowcount == 0:
    return jsonify({"error": "version_conflict"}), 409
```

## Part 3 — Enforce Active Doctor Access in Landing Routes

Even after the June 27 CORS and identity fixes, the landing portal's proxy routes
(`/prescriptions`, `/lab_reports`, `/view_patient`) were still forwarding requests
to the backend without checking whether the doctor's access was currently active.

```python
# portals/landing.py — applied to all 3 proxy routes

def _assert_active_doctor_access(doctor_id: str, patient_id: str) -> bool:
    """Returns True only if there is a non-expired approved access record."""
    resp = backend_get(f"/api/access/check?doctor={doctor_id}&patient={patient_id}")
    if resp.status_code != 200:
        return False
    data = resp.json()
    return data.get("active", False)

@landing_bp.route("/view_patient/<patient_id>")
@_require_portal_session(role="doctor")
def view_patient(patient_id):
    doctor_id = session["user_id"]
    if not _assert_active_doctor_access(doctor_id, patient_id):
        return render_template("access_denied.html"), 403
    # Proceed to proxy the data
    ...
```

This closes the gap where a doctor with an expired session could still fetch data
by calling the landing proxy route directly, bypassing the UI expiry badge.

## Part 4 — Vitals History Tracking

Added timestamped vitals recording to the EMR. Each reading is appended to the
`vitals_history` JSONB array (from Migration 003) rather than overwriting a single row.

#### Schema of a vitals entry

```json
{
  "recorded_at":    "2026-06-28T17:55:00Z",
  "recorded_by":    "doctor_uuid",
  "blood_pressure": "120/80",
  "heart_rate":     72,
  "spo2":           98,
  "temperature":    36.6,
  "weight_kg":      74.2,
  "notes":          "Post-op check, stable"
}
```

#### Append endpoint

```python
@emr_bp.route("/vitals/<patient_id>", methods=["POST"])
@_require_jwt(roles=["doctor"])
def add_vitals(patient_id):
    pid = _resolve_pid(patient_id)
    doctor_id = request.jwt_payload["uid"]

    # Enforce active access
    if not _has_active_access(doctor_id, pid):
        return jsonify({"error": "access_expired"}), 403

    entry = {
        "recorded_at": datetime.utcnow().isoformat() + "Z",
        "recorded_by": doctor_id,
        **{k: request.json[k] for k in
           ["blood_pressure","heart_rate","spo2","temperature","weight_kg","notes"]
           if k in request.json}
    }

    db.execute("""
        UPDATE patient_profiles
        SET vitals_history = vitals_history || :entry::jsonb
        WHERE patient_id = :pid
    """, {"entry": json.dumps([entry]), "pid": pid})
    db.commit()
    return jsonify({"status": "recorded"}), 201
```

The `||` operator in PostgreSQL appends to a JSONB array in a single atomic update —
no read-modify-write race condition.

#### Frontend — Vitals Timeline

```javascript
function renderVitalsTimeline(history) {
  return history
    .slice()
    .reverse()                        // most recent first
    .map(v => `

          <span>Temp: ${v.temperature ?? '—'} °C</span>
```

## Questions I Still Have

- Should vitals history be stored in a separate `vitals` table instead of JSONB on `patient_profiles`? JSONB is convenient but can't be indexed per-field — a separate table would allow `WHERE heart_rate > 100` queries.
- The legacy CBC→GCM upgrade only happens on the next write. Should there be a one-time migration script that upgrades all existing records immediately?
- `record_version` integer will eventually overflow on very frequently updated records. Should it be `BIGINT`?
