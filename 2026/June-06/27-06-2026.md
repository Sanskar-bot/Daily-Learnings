## Part 1 — Bug: Inconsistent Password Hashing Across Portals

#### The problem

When a patient registered via `portals/patient_portal.py`, their password was hashed
with werkzeug's `pbkdf2:sha256`. But when they logged in via `portals/landing.py`,
the route called `hashlib.sha256(password.encode()).hexdigest()` — a raw SHA-256 with
no salt and no stretching. The hashes never matched, so login always failed for users
registered through the patient portal.

```
Registration path:   patient_portal.py  → werkzeug pbkdf2:sha256 → stored in DB
Login path:          landing.py         → hashlib SHA-256         → compared → ❌ mismatch
```

#### Fix — single `hash_password()` function everywhere

```python
# portals/auth_utils.py
from werkzeug.security import generate_password_hash, check_password_hash

def hash_password(raw: str) -> str:
    return generate_password_hash(raw, method="pbkdf2:sha256", salt_length=16)

def verify_password(raw: str, stored_hash: str) -> bool:
    return check_password_hash(stored_hash, raw)
```

All four registration/login entry points now import from `auth_utils`:

```python
# portals/landing.py   — was using hashlib.sha256()
from portals.auth_utils import hash_password, verify_password

def register_patient():
    ...
    pw_hash = hash_password(request.form["password"])   # ✅

def login():
    ...
    if not verify_password(request.form["password"], user["pw_hash"]):
        return redirect("/login?error=invalid")
```

Werkzeug's `generate_password_hash` uses PBKDF2-HMAC-SHA256 with a random 16-byte salt
and 260,000 iterations by default — far stronger than a single round of SHA-256.

## Part 2 — Bug: CORS Wildcard `Access-Control-Allow-Origin: *`

Both the patient portal and doctor portal were returning `*` on every response, allowing
any origin to make credentialed cross-origin requests to the API.

#### Why wildcard is dangerous with credentials

`Access-Control-Allow-Origin: *` + `Access-Control-Allow-Credentials: true` is
actually forbidden by the spec and rejected by browsers — but the combination signals
a misconfiguration that's easy to exploit in non-browser clients (Postman, curl, scripts).
Any website could make unauthenticated requests to the API endpoints.

#### Fix — environment-controlled origin allowlist

```python
# portals/auth_utils.py
import os

ALLOWED_ORIGINS = set(
    os.environ.get("MEDVAULT_ALLOWED_ORIGINS", "http://localhost:5000").split(",")
)
# Always include local dev origins
ALLOWED_ORIGINS.update({
    "http://localhost:5000",
    "http://localhost:5001",
    "http://127.0.0.1:5000",
})

def cors_after_request(response):
    origin = request.headers.get("Origin", "")
    if origin in ALLOWED_ORIGINS:
        response.headers["Access-Control-Allow-Origin"]      = origin
        response.headers["Access-Control-Allow-Credentials"] = "true"
        response.headers["Vary"]                             = "Origin"
    # If origin not in allowlist — no CORS header → browser blocks the request
    return response
```

```python
# portals/patient_portal.py
from portals.auth_utils import cors_after_request

@patient_bp.after_request
def _cors(response):
    return cors_after_request(response)
```

The `Vary: Origin` header tells CDNs and proxies not to cache a response for one
origin and serve it to another.

## Part 3 — Bug: Patient Identity Mismatch (`profile_code` vs UUID)

#### The problem

The system had two ways to identify a patient:
- `user_id` — the UUID primary key in `users` (the authoritative identifier)
- `profile_code` — a short human-readable code like `PT-3892` stored in `patient_profiles`

Some routes used one, some used the other. The prescription and lab-report proxy routes
in `landing.py` were passing `profile_code` to the backend, but the EMR endpoints
expected `user_id`. Queries returned no results — silently, with no error.

#### Fix — resolver helpers

```python
# server/server.py
def _resolve_patient_uuid(identifier: str) -> str | None:
    """Accept either a UUID or a profile_code, always return UUID."""
    # Try UUID first
    row = db.execute(
        "SELECT user_id FROM users WHERE user_id = :id", {"id": identifier}
    ).fetchone()
    if row:
        return row["user_id"]
    # Fall back to profile_code
    row = db.execute(
        "SELECT patient_id FROM patient_profiles WHERE profile_code = :pc",
        {"pc": identifier}
    ).fetchone()
    return row["patient_id"] if row else None

def _resolve_doctor_uuid(identifier: str) -> str | None:
    """Same pattern for doctors."""
    ...

# Exposed via app.config for use in blueprints
app.config["resolve_patient_uuid"] = _resolve_patient_uuid
app.config["resolve_doctor_uuid"]  = _resolve_doctor_uuid
```

```python
# server/emr/routes.py — applied at entry of all 6 patient-scoped endpoints
def _resolve_pid(raw_id: str) -> str | None:
    return current_app.config["resolve_patient_uuid"](raw_id)

@emr_bp.route("/profile/<patient_id>")
@_require_jwt()
def get_profile(patient_id):
    pid = _resolve_pid(patient_id)
    if not pid:
        return jsonify({"error": "patient_not_found"}), 404
    ...
```

```python
# portals/landing.py — pass UUID, not profile_code
def patient_prescriptions_direct():
    pid = session.get("user_id")    # UUID stored at login — was session["profile_code"]
    resp = backend_get(f"/emr/prescriptions/{pid}")
    ...
```

## Part 4 — What I Learned About Identity Resolution Patterns

The `_resolve_patient_uuid` pattern is a common idiom in systems that have legacy
or user-facing identifiers alongside database primary keys:

| Pattern | Trade-off |
|---|---|
| Always use UUID internally | Cleanest, but breaks human-readable codes in URLs |
| Always use profile_code | Human-readable URLs, but requires extra DB lookup everywhere |
| Resolver at boundary | Convert at the entry point, use UUID internally — best of both |

The resolver belongs at the **entry point** (route handler), not scattered throughout
service logic. Once inside the handler, only UUIDs flow through the call chain.

## Questions I Still Have

- Should `profile_code` be deprecated entirely in favour of always using UUID in URLs? Short codes are nicer for sharing (`PT-3892`) but add complexity.
- CORS: should `OPTIONS` preflight requests be handled explicitly, or is Flask-CORS / `after_request` enough?
- The resolver does two DB queries in the worst case (UUID check + profile_code fallback). For high-traffic endpoints, would it be worth caching the mapping in Redis?
