## Part 1 — Windows DPAPI (Data Protection API)

DPAPI is a Windows OS service that encrypts data tied to the **current user account**.
The encryption key is derived from the user's login credentials and managed entirely
by the OS — the application never sees or handles the master key.

#### How it works under the hood

```
DPAPI key derivation (simplified):
  master_key = PBKDF2(user_login_password, user_SID_salt)
  ciphertext  = AES-256-CBC(data, master_key, random_IV)
  output      = { IV | ciphertext | HMAC-SHA1(IV + ciphertext) }
```

The application calls `CryptProtectData` / `CryptUnprotectData` via the Windows API.
The OS handles key derivation, encryption, and MAC verification entirely internally.

#### Python binding — `pywin32`

```python
# common/secure_key_store.py  (Windows branch)
import win32crypt

def store_private_key(key_pem: bytes, label: str) -> None:
    encrypted = win32crypt.CryptProtectData(
        key_pem,
        label,              # description string (shown in Credential Manager)
        None,               # optional entropy (extra passphrase)
        None,               # reserved
        None,               # prompt struct
        0                   # flags: 0 = user scope (not machine scope)
    )
    key_path = _key_path(label)
    key_path.write_bytes(encrypted)

def load_private_key(label: str) -> bytes:
    encrypted = _key_path(label).read_bytes()
    key_pem, _ = win32crypt.CryptUnprotectData(
        encrypted, None, None, None, 0
    )
    return key_pem
```

Key properties:
- Decryption only works on the **same machine**, by the **same Windows user**
- Moving the encrypted file to another machine renders it permanently undecryptable
- No password prompt — seamless UX, but tied to the OS login session

#### Security scope: user vs. machine

```python
# User scope (flag=0): only the current user can decrypt
# Machine scope (flag=CRYPTPROTECT_LOCAL_MACHINE): any user on the machine can decrypt
# MedVault always uses user scope — private keys are per-user, not per-machine
```

## Part 2 — Linux / macOS Fallback: AES-256-GCM with Argon2id

DPAPI is Windows-only. The fallback for Linux/macOS uses a machine-derived key
with Argon2id (memory-hard KDF) to encrypt the private key file.

#### Machine key derivation

```python
import platform, hashlib
from pathlib import Path

def _derive_machine_key(salt: bytes) -> bytes:
    """
    Derive a 256-bit key from a machine-specific secret using Argon2id.
    The machine secret is /etc/machine-id on Linux, platform.node() on macOS.
    This is software-only protection — no hardware TPM involved.
    """
    if platform.system() == "Linux":
        machine_secret = Path("/etc/machine-id").read_text().strip().encode()
    else:
        machine_secret = platform.node().encode()  # hostname on macOS

    import argon2.low_level as argon2_ll
    return argon2_ll.hash_secret_raw(
        secret=machine_secret,
        salt=salt,
        time_cost=3,
        memory_cost=65536,   # 64 MB
        parallelism=4,
        hash_len=32,
        type=argon2_ll.Type.ID
    )
```

#### File format

```
Byte layout of the stored key file:
  [0:16]   salt       (16 random bytes, for Argon2id)
  [16:28]  nonce      (12 random bytes, for AES-GCM)
  [28:]    ciphertext (AES-256-GCM encrypted private key PEM)
            └── GCM auth tag is the last 16 bytes of ciphertext
```

```python
from cryptography.hazmat.primitives.ciphers.aead import AESGCM
import os

def store_private_key_linux(key_pem: bytes, label: str) -> None:
    salt  = os.urandom(16)
    nonce = os.urandom(12)
    key   = _derive_machine_key(salt)
    ct    = AESGCM(key).encrypt(nonce, key_pem, label.encode())
    _key_path(label).write_bytes(salt + nonce + ct)
    import warnings
    warnings.warn(
        "Private key is protected by software-only AES-GCM (machine-derived key). "
        "For production use, consider a hardware security module (HSM) or OS keychain.",
        UserWarning, stacklevel=2
    )

def load_private_key_linux(label: str) -> bytes:
    raw   = _key_path(label).read_bytes()
    salt  = raw[:16];  nonce = raw[16:28];  ct = raw[28:]
    key   = _derive_machine_key(salt)
    return AESGCM(key).decrypt(nonce, ct, label.encode())
```

The GCM auth tag means any tampering with the ciphertext causes decryption to raise
`InvalidTag` rather than silently returning corrupted key bytes.

## Part 3 — Unified `secure_key_store.py` Interface

The calling code (`client/`, `doctor/`) never branches on OS — it always calls:

```python
from common.secure_key_store import store_private_key, load_private_key

# Registration
store_private_key(priv_key_pem, label=f"medvault:{user_id}")

# Login / decryption
priv_key_pem = load_private_key(label=f"medvault:{user_id}")
```

Internally the module dispatches:

```python
import platform

def store_private_key(key_pem: bytes, label: str) -> None:
    if platform.system() == "Windows":
        _store_dpapi(key_pem, label)
    else:
        _store_aes_gcm(key_pem, label)

def load_private_key(label: str) -> bytes:
    if platform.system() == "Windows":
        return _load_dpapi(label)
    else:
        return _load_aes_gcm(label)
```

## Part 4 — Why Not Just Use a Password?

A natural question: why not just ask the user for a passphrase to protect the private key?
Explored the tradeoffs:

| Approach | UX | Security | Risk |
|---|---|---|---|
| DPAPI (Windows) | Seamless — no prompt | OS-backed, tied to user login | Compromised OS session = key exposed |
| AES-GCM + machine key | Seamless — no prompt | Software-only | Malware on same machine = key exposed |
| Password-protected (PKCS#8) | Prompt on every use | Best (knowledge factor) | Weak passwords, user friction |
| Hardware key (YubiKey) | Tap on use | Strongest | Cost, complexity |

MedVault's current choice (DPAPI / machine-key AES-GCM) optimises for developer-demo
UX. A production deployment would layer in PKCS#8 passphrase protection or a hardware key.
