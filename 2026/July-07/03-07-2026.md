## Part 1 — The Private Key Loss Problem

MedVault's zero-knowledge design means the server never holds the AES key that
encrypts patient records. If a patient loses their RSA private key (device wipe,
OS reinstall), their records become permanently inaccessible — the server cannot help.

This is a fundamental trade-off in zero-knowledge systems:
- **More security** → the server can't recover your data if you lose your key
- **More convenience** → the server holds a recovery key (negates zero-knowledge)

MedVault's recovery approach: **key escrow with patient-controlled encryption**.

#### Recovery Key Design

```
At registration:
  1. Generate RSA keypair (pub, priv)
  2. Generate a 32-byte recovery secret                → recovery_secret
  3. Encrypt priv key with recovery_secret             → encrypted_priv (AES-GCM)
  4. Store encrypted_priv on server                   → server never sees priv_key
  5. Display recovery_secret to patient once          → patient writes it down / saves offline
  6. Hash recovery_secret with Argon2id               → recovery_hash
  7. Store recovery_hash on server                    → for verification only

Recovery flow:
  1. Patient enters recovery_secret in the UI
  2. Server verifies Argon2id(recovery_secret) == stored recovery_hash
  3. Server returns encrypted_priv
  4. Client decrypts encrypted_priv with recovery_secret → priv_key
  5. Patient can now access their records again
```

The server stores `encrypted_priv` (useless without `recovery_secret`) and
`recovery_hash` (used only for verification). The `recovery_secret` itself never
leaves the client after registration.

#### Implementation

```python
# common/crypto_utils.py

def generate_recovery_package(priv_key_pem: bytes) -> dict:
    recovery_secret = os.urandom(32)                     # 256-bit random secret
    secret_b64      = base64.urlsafe_b64encode(recovery_secret).decode()

    # Encrypt the private key with the recovery secret
    nonce         = os.urandom(12)
    encrypted_priv = AESGCM(recovery_secret).encrypt(nonce, priv_key_pem, None)
    encrypted_b64  = base64.b64encode(nonce + encrypted_priv).decode()

    # Hash for server-side verification (never store the secret itself)
    import argon2.low_level as argon2_ll
    salt = os.urandom(16)
    recovery_hash = argon2_ll.hash_secret_raw(
        secret=recovery_secret, salt=salt,
        time_cost=3, memory_cost=65536, parallelism=4,
        hash_len=32, type=argon2_ll.Type.ID
    )
    hash_b64 = base64.b64encode(salt + recovery_hash).decode()

    return {
        "recovery_secret":   secret_b64,      # shown to patient once, then discarded
        "encrypted_priv":    encrypted_b64,   # stored on server
        "recovery_hash":     hash_b64,        # stored on server for verification
    }
```

## Part 3 — EMR Metadata Persistence

Three metadata fields were being computed on-the-fly per request but not persisted:

| Field | Before | After |
|---|---|---|
| `completeness_pct` | Computed on every `/emr/profile` fetch | Computed on profile write, stored in DB |
| `record_version` | Not tracked | Incremented on every `UPDATE`, stored |
| `last_updated` | Not tracked | Set by PostgreSQL trigger on `UPDATE` |

#### Completeness recomputation on write

```python
# server/emr/routes.py — upsert_patient_profile()

PROFILE_FIELDS = [
    "name", "dob", "blood_type", "allergies",
    "emergency_contact", "phone", "address"
]

def _compute_completeness(profile: dict) -> int:
    filled = sum(1 for f in PROFILE_FIELDS if profile.get(f) and str(profile[f]).strip())
    return round(filled / len(PROFILE_FIELDS) * 100)

@emr_bp.route("/profile/<patient_id>", methods=["PUT"])
@_require_jwt()
def upsert_patient_profile(patient_id):
    ...
    completeness = _compute_completeness(body)
    db.execute("""
        INSERT INTO patient_profiles (patient_id, ..., completeness_pct, record_version)
        VALUES (:pid, ..., :pct, 1)
        ON CONFLICT (patient_id) DO UPDATE
        SET ...,
            completeness_pct = :pct,
            record_version   = patient_profiles.record_version + 1
        -- last_updated set automatically by trigger
    """, {**body, "pid": patient_id, "pct": completeness})
```

#### Why persist instead of compute on read?

- Avoids recomputation on every `GET /emr/profile` — especially important when
  the profile is fetched on every page load
- Allows sorting/filtering patients by completeness percentage in the doctor's view:
  `ORDER BY completeness_pct ASC` now works efficiently with an index

## Part 4 — Unified Appointments Model

The system had two separate appointment data sources:
- `server/emr/` — encrypted appointment records in the EMR
- `portals/landing.py` — a separate appointments table for scheduling

Unified into a single model flowing through the EMR:

```sql
CREATE TABLE appointments (
    appointment_id  UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    patient_id      UUID REFERENCES users(user_id),
    doctor_id       UUID REFERENCES users(user_id),
    scheduled_at    TIMESTAMPTZ NOT NULL,
    duration_mins   INTEGER DEFAULT 30,
    status          TEXT DEFAULT 'scheduled',  -- scheduled | completed | cancelled | no_show
    notes           TEXT,
    created_at      TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_appointments_patient_scheduled
ON appointments (patient_id, scheduled_at);

CREATE INDEX idx_appointments_doctor_scheduled
ON appointments (doctor_id, scheduled_at);
```

Both the patient portal and the doctor portal now read from this single table —
eliminating the scenario where a doctor cancelled an appointment in the EMR but it
still showed as scheduled in the landing portal's separate table.

## Questions I Still Have

- The recovery secret is 32 bytes (256 bits) of randomness. Should it be displayed as hex, base64url, or a BIP39-style mnemonic phrase (more human-memorable, easier to write down)?
- What happens if the patient forgets both their password *and* their recovery secret? Is that a permanent lock-out? (Answer: yes, by design — but this needs to be communicated clearly at registration.)
- The `appointments` table doesn't encrypt appointment data. Should appointment notes be encrypted client-side (they could contain sensitive clinical information)?
