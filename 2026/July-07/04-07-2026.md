## Part 2 — What Worked Well

#### 1. Zero-Knowledge Architecture Held

The server-side zero-access guarantee — that the server never touches plaintext
patient records — held through 13 days of feature additions and security fixes. Every
new endpoint was reviewed against this constraint before merging.

The key discipline: **never accept decrypted data from the client**. All
endpoints receive ciphertext and encrypted key blobs. Decryption happens entirely
on the patient's or doctor's device.

#### 2. Layered Security Approach

Each security fix added a *layer*, not a replacement:

```
Layer 1: JWT authentication (who are you?)
Layer 2: Role check (are you a patient or doctor?)
Layer 3: Ownership check (is this your record?)
Layer 4: Active-access check (do you have a current grant?)
Layer 5: Expiry check (has the grant TTL elapsed?)
Layer 6: Audit log (what did you do, and when?)
```

A bug in any single layer is caught by the next. Defence in depth.

#### 3. The Resolver Pattern

The `_resolve_patient_uuid()` boundary resolver pattern (introduced June 27) proved
its value every time a new endpoint was added — there was never a question of "which
identifier should I use here?" because all internal code uses UUIDs, and the conversion
happens at the API boundary automatically.

## Part 3 — What I'd Do Differently

#### 1. Design the Database Schema First

The three schema migrations on June 28 (`last_updated`, `record_version`,
`vitals_history`) were all fields that should have been in the initial schema. Adding
columns mid-development with `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` is safe, but
it's a signal that the data model wasn't fully designed upfront.

**Lesson:** Before writing a single line of application code, write the complete
database schema including all foreign keys, indexes, and triggers. It's much easier
to change a schema diagram than a live database.

#### 2. Write the Security Model Before the Feature Code

All 25 security issues were identified and fixed *after* the features were built —
a classic "build first, secure later" pattern. If the security model (JWT decorator,
access guard, CORS policy, status allowlist) had been written first as empty stubs
and then filled in, the IDOR vulnerability and the CORS wildcard would never have
shipped in the first place.

**Lesson:** Define the `@_require_jwt`, `@_caller_may_access_patient`, and
`@rate_limited` decorators on Day 1, even if the implementations are `pass` stubs.
Apply them to every route from the start. Fill in the logic incrementally.

#### 3. Test on Multiple Platforms from Day 1

The DPAPI/AES-GCM platform split in `secure_key_store.py` was implemented on Day 3
but not tested on Linux until Day 8 — when the integration tests ran in a Docker
container and immediately failed because `cryptography.hazmat.primitives.ciphers.aead`
wasn't imported correctly in the Linux branch.

## Part 4 — MedVault v2 Roadmap

#### Tier 1 — High Value, Near-Term

1. **IPFS or hybrid-cloud storage** — upload encrypted record blobs to IPFS so the
   MedVault server isn't a single point of failure for ciphertext storage.
2. **QR code access grants** — patient generates a time-limited QR code in the app;
   doctor scans it to receive a pre-wrapped AES key without manual request/approval flow.
3. **Mobile app** — React Native or Flutter client with biometric unlock (Face ID /
   fingerprint) for the private key, replacing the DPAPI/AES-GCM desktop-only solution.

#### Tier 2 — Significant Engineering

4. **Federated identity** — integrate with hospital identity providers (SAML / OIDC)
   so doctors authenticate with their hospital credentials, not a separate MedVault account.
5. **Selective disclosure** — allow patients to share only specific sections of their EMR
   (e.g. "allergies only") by encrypting each section with a separate AES key.
6. **Blockchain audit log** — anchor the audit log to a public blockchain (Ethereum,
   Polygon) for tamper-evident, patient-verifiable access history.

#### Tier 3 — Research / Experimental

7. **Homomorphic encryption** — allow the server to compute aggregate statistics
   (e.g. average blood pressure across a cohort) without decrypting individual records.
8. **Zero-knowledge proofs** — allow a doctor to prove they have a valid access grant
   without revealing which patient or which doctor, for privacy-preserving audit reporting.

## Part 5 — Self-Assessment

Looking back at the original problem statement — *"centralized health data storage
leads to breaches, exploitation, and patient disempowerment"* — MedVault addresses
the core issues:

- **Breaches**: Server compromise reveals only encrypted blobs — useless without patient keys ✅
- **Exploitation**: No plaintext records → nothing to sell to data brokers ✅
- **Patient control**: Patients grant and revoke access explicitly, with TTLs ✅
- **Transparency**: Audit log records every access event ✅
- **Data loss**: Encrypted backups possible (recovery key flow) ✅

The remaining gap is **usability** — the current system requires technical setup
(key generation, DPAPI, local storage) that a real patient would find overwhelming.
That's the v2 mandate: make the same security model accessible to non-technical users.

## Questions I Still Have

- Is IPFS the right decentralised storage layer, or is something like Filecoin (incentivised IPFS) or Arweave (permanent storage) better for medical records that need long-term accessibility?
- Selective disclosure with per-section AES keys multiplies the number of wrapped keys the server stores by the number of sections (7 sections × N doctors). Is there a more efficient cryptographic construction (e.g. ABE — Attribute-Based Encryption)?
- At what point does MedVault move from "portfolio project" to "responsible disclosure" — i.e. should the real-world security gaps (no TLS enforcement in dev, no HSM for key storage) be prominently documented before sharing publicly?
