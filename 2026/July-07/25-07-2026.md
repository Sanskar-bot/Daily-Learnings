## What I Learned

### MedVault v2 — Broken Access Control on File Upload & Patient Reports

> **Context:** Security audit of the v2 endpoints revealed that the approval-
> gated access control added in v1 was not applied to the new file upload and
> report endpoints added during v2. Any authenticated doctor could read or
> write any patient's files without an approved access grant. Fixed today.

---

## Part 1 — The Vulnerability

Three endpoints were missing the `_has_active_access` check:

| Endpoint | Issue |
|---|---|
| `POST /reports/upload` | Any authenticated doctor could upload a report to any patient's record |
| `GET /reports/patient/<patient_id>` | Any authenticated doctor could read any patient's reports |
| `POST /images/upload` | Any authenticated doctor could upload images to any patient's record |

This is the same **IDOR (Insecure Direct Object Reference)** class of vulnerability fixed in v1 — but the new v2 endpoints were added without applying the existing guard, a classic "new code, old vulnerability" pattern.

---

## Part 2 — Fix: Apply `_has_active_access` to All Patient-Scoped Endpoints

```python
# POST /reports/upload — before
@reports_bp.route("/upload", methods=["POST"])
@_require_jwt(roles=["doctor"])
def upload_report():
    patient_id = request.json["patient_id"]
    # No access check — any doctor could write to any patient!
    _db_write_report(patient_id, ...)

# After
@reports_bp.route("/upload", methods=["POST"])
@_require_jwt(roles=["doctor"])
def upload_report():
    patient_id = request.json["patient_id"]
    if not _has_active_access(patient_id):          # ← added
        return jsonify({"error": "access_denied"}), 403
    _db_write_report(patient_id, ...)
```

For `GET /reports/patient/<patient_id>`, added a role split:
- **Patient role:** can only access `patient_id == their own uid`
- **Doctor role:** must have `_has_active_access(patient_id)` → approved + non-expired grant in `wrapped_keys`

For `POST /images/upload`, added both:
1. A `_db_get_record` existence check → 404 if the patient doesn't exist
2. `_has_active_access` → 403 if the doctor doesn't have a grant

The existence check matters because without it, a doctor could probe patient IDs to discover which IDs are valid (information leakage), even without reading the actual data.

---

## Part 3 — Lesson: Security Review Checklist for New Endpoints

Every time a new patient-scoped endpoint is added, it must be checked against:

```
[ ] @_require_jwt() decorator applied
[ ] Role check: is this endpoint doctor-only, patient-only, or both?
[ ] If doctor: _has_active_access(patient_id) check
[ ] If patient: uid == patient_id check
[ ] If writing: existence check before write (404 before 403)
[ ] Audit log entry: record who accessed what and when
```

The root cause was the absence of this checklist — new routes were added quickly without running through the security requirements.

## What I Practiced / Built

- Identified IDOR vulnerability across 3 new v2 endpoints (upload, reports, images)
- Applied `_has_active_access` guard to all patient-scoped write endpoints
- Added role-split logic to the reports read endpoint (patient self-only vs doctor active-grant)
- Added existence check (404) before access check (403) on image upload
- Formalised a security checklist for new endpoints to prevent future regressions

## Questions I Still Have

- Should `_has_active_access` be a decorator (`@require_patient_access`) rather than a function call? A decorator would be harder to forget — you'd have to actively remove it rather than just not add it.
- The existence check before the access check reveals that the patient ID exists (because it returns 404 vs 403). Is that information leakage? Should it return 403 regardless of whether the patient exists?
