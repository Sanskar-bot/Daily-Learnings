## Part 1 — Registration UX Enhancements

Replaced the bare registration form with a hardened, user-friendly version:

- **Real-time uniqueness check:** `GET /auth/check_username?username=x` — called on blur, shows "already taken" inline before form submission
- **Confirm password field:** Client-side validation, no submit if mismatch
- **Country code selector:** Phone number split into `+91` prefix + number — improves Twilio routing accuracy
- **Inline error messages:** Each field shows its own error (`"Email already in use"`, `"Password too short"`) instead of a generic alert at the top

Also fixed a critical upsert bug: the `ON CONFLICT DO UPDATE` logic in the registration route was silently overwriting existing accounts when there was a username collision. Replaced with a strict `INSERT ... WHERE NOT EXISTS` pattern:

```python
# Before — dangerous upsert
"INSERT INTO users ... ON CONFLICT(username) DO UPDATE SET ..."

# After — safe check
existing = db.execute("SELECT id FROM users WHERE username=:u", {"u": username}).fetchone()
if existing:
    return jsonify({"error": "username_taken"}), 409
db.execute("INSERT INTO users ...")
```

## Part 2 — Post-Registration Onboarding Wizard

New 5-step patient wizard triggered immediately after registration:

| Step | Content | Required? |

| 2 | Known risks (chronic conditions, medications) | ✓ Required |

Key implementation detail: the patient's password is stored in `sessionStorage` as a one-shot relay (read immediately and deleted) so the onboarding page can encrypt the initial health record without asking for the password again.

Schema additions:
```sql
ALTER TABLE users ADD COLUMN IF NOT EXISTS onboarding_status TEXT DEFAULT 'pending';
ALTER TABLE users ADD COLUMN IF NOT EXISTS onboarding_completed_at TIMESTAMP;
```

The dashboard shows a nudge banner based on `onboarding_status`: urgent for `pending`, soft for `minimum_done` or `skipped`, hidden for `complete`.

## Part 3 — Multi-Worker Migration Deadlock Fix

On Railway with multiple gunicorn workers, all workers ran the migration check on startup simultaneously, causing deadlocks:

```
ERROR: deadlock detected — two workers both trying to ALTER TABLE users simultaneously
```

**Fix:** PostgreSQL advisory locks — a session-scoped distributed mutex:

```python
def run_migrations_if_needed():
    # Try to acquire advisory lock (non-blocking)
    acquired = db.execute(
        "SELECT pg_try_advisory_lock(123456789)"
    ).scalar()

    if not acquired:
        # Another worker is running migrations — skip
        return

    try:
        _run_ddl_statements()
    finally:
        db.execute("SELECT pg_advisory_unlock(123456789)")
```

`pg_try_advisory_lock` is non-blocking (returns `false` immediately if another session holds it) — unlike `pg_advisory_lock` which would block. This ensures exactly one worker runs migrations per restart.

## Questions I Still Have

- `sessionStorage` for the one-shot password relay is cleared on page close — but what if the user closes the tab mid-onboarding? They'd need to re-enter their password on the next visit. Should there be a "complete onboarding" link on the dashboard that prompts for the password?
- Advisory lock ID `123456789` is hardcoded. If MedVault is deployed alongside another app using the same lock ID, they'd conflict. Should it be a hash of the app name?
