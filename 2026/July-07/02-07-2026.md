## Part 1 — Finding Slow Queries with `EXPLAIN ANALYZE`

PostgreSQL's `EXPLAIN ANALYZE` runs the query and reports actual execution time,
not just the planner's estimate:

```sql
-- Profiling the active-access check query
EXPLAIN ANALYZE
SELECT 1
FROM access_requests ar
JOIN wrapped_keys wk ON wk.request_id = ar.request_id
WHERE ar.doctor_id  = '3f2a1b4c-...'
  AND ar.patient_id = '9a1b2c3d-...'
  AND ar.status     = 'approved'
  AND wk.expires_at > NOW()
LIMIT 1;
```

Output revealed a **Seq Scan** on `access_requests` (240ms on 10,000 rows) because
there was no index on `(doctor_id, patient_id, status)`. The planner was scanning
every row and filtering in memory.

## Part 2 — Indexing Strategy

#### Composite index for the access check

```sql
-- The hot path: "does doctor D have active access to patient P?"
CREATE INDEX CONCURRENTLY idx_access_requests_doctor_patient_status
ON access_requests (doctor_id, patient_id, status);

-- Why this column order?
-- 1. doctor_id has highest selectivity in our workload (most queries filter by logged-in doctor)
-- 2. patient_id narrows further
-- 3. status is low-cardinality ('pending'|'approved'|'denied'|'expired') — put last in composite
```

After index creation, the same `EXPLAIN ANALYZE` showed an **Index Scan** at 0.3ms —
800× improvement.

#### Partial index for the expiry check

```sql
-- Only index rows where status = 'approved' (the only status we ever JOIN on)
CREATE INDEX CONCURRENTLY idx_wrapped_keys_active
ON wrapped_keys (patient_id, doctor_id, expires_at)
WHERE expires_at > NOW();   -- partial index — automatically excluded expired rows
```

A partial index is smaller (fewer rows) and faster than a full index. The planner
will use it whenever the query's WHERE clause implies `expires_at > NOW()`.

#### Other indexes added

```sql
-- Fast lookup of a patient's full prescription history
CREATE INDEX idx_prescriptions_patient_created
ON prescriptions (patient_id, created_at DESC);

-- Fast lookup of audit log by actor (doctor) and timestamp
CREATE INDEX idx_audit_log_actor_ts
ON audit_log (actor_id, ts DESC);

-- Unique constraint to prevent duplicate active access grants
CREATE UNIQUE INDEX idx_wrapped_keys_active_unique
ON wrapped_keys (patient_id, doctor_id)
WHERE expires_at > NOW();
```

The last one prevents a patient from accidentally granting access to the same doctor
twice simultaneously — the `INSERT` would fail with a unique constraint violation
instead of silently creating a duplicate.

## Part 3 — Connection Pooling with `psycopg2` + `ThreadedConnectionPool`

The current setup creates a new database connection per Flask request — fine for
local dev but catastrophic in production (each connection takes ~5ms to establish,
PostgreSQL has a default max of 100 connections).

```python
# server/db.py — before: one connection per request
import psycopg2

def get_db():
    return psycopg2.connect(os.environ["DATABASE_URL"])
```

#### Fix — threaded connection pool

```python
# server/db.py — after: pool of reusable connections
from psycopg2 import pool as pg_pool

_pool: pg_pool.ThreadedConnectionPool | None = None

def init_pool(min_conn: int = 2, max_conn: int = 10) -> None:
    global _pool
    _pool = pg_pool.ThreadedConnectionPool(
        minconn=min_conn,
        maxconn=max_conn,
        dsn=os.environ["DATABASE_URL"]
    )

class PooledConnection:
    """Context manager that checks out and returns a connection to the pool."""
    def __enter__(self):
        self.conn = _pool.getconn()
        return self.conn.cursor(cursor_factory=psycopg2.extras.RealDictCursor)

    def __exit__(self, exc_type, *_):
        if exc_type:
            self.conn.rollback()
        else:
            self.conn.commit()
        _pool.putconn(self.conn)

# Usage in routes
def get_profile(patient_id):
    with PooledConnection() as cur:
        cur.execute("SELECT * FROM patient_profiles WHERE patient_id=%s", (patient_id,))
        row = cur.fetchone()
    return jsonify(dict(row))
```

`ThreadedConnectionPool` is thread-safe — each Flask worker thread gets its own
connection from the pool, holds it for the duration of the request, and returns it.
The pool automatically blocks (with a configurable timeout) if all connections are
in use.

## Part 4 — Query Result Caching (Patient Profile)

The patient profile is read on nearly every page load but written rarely (once per
update). Caching it in Flask's application context avoids repeated DB reads within
the same request:

```python
# server/db.py

from flask import g

def get_cached_profile(patient_id: str) -> dict:
    """Cache profile in Flask's g context — lives for one request."""
    cache_key = f"profile:{patient_id}"
    if cache_key not in g:
        with PooledConnection() as cur:
            cur.execute("SELECT * FROM patient_profiles WHERE patient_id=%s", (patient_id,))
            g[cache_key] = dict(cur.fetchone() or {})
    return g[cache_key]
```

Flask's `g` object is request-scoped — it's created fresh for each request and
destroyed at the end. This is safe single-request caching with no stale-data risk.

## Questions I Still Have

- `CONCURRENTLY` index creation doesn't lock the table but takes longer. How do I know when it's safe to run a `CONCURRENTLY` migration in production without impacting live traffic?
- The partial index `WHERE expires_at > NOW()` won't include rows that expire in the future — but PostgreSQL materialises the index at creation time. Does it automatically exclude newly-expired rows, or does it need a `REINDEX`?
- For a real production deployment, should connection pooling be handled at the application layer (psycopg2 pool) or the infrastructure layer (PgBouncer)? PgBouncer can pool across multiple app servers.
