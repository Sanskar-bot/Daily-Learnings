## Part 1 — RSA Key Size: 2048 → 4096 bits

#### Why 2048-bit is no longer enough

NIST SP 800-57 recommends 2048-bit RSA keys provide approximately 112 bits of security
— acceptable through 2030 but not beyond. 4096-bit RSA provides ~140 bits of security
and is increasingly standard for long-lived keys like the patient private keys in MedVault
(a patient's key might need to protect records for decades).

```python
# common/crypto_utils.py — before
def generate_rsa_keypair(key_size: int = 2048) -> tuple[bytes, bytes]:
    ...

# After
def generate_rsa_keypair(key_size: int = 4096) -> tuple[bytes, bytes]:
    private_key = rsa.generate_private_key(
        public_exponent=65537,
        key_size=key_size,
    )
    pub_pem  = private_key.public_key().public_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PublicFormat.SubjectPublicKeyInfo
    )
    priv_pem = private_key.private_bytes(
        encoding=serialization.Encoding.PEM,
        format=serialization.PrivateFormat.PKCS8,
        encryption_algorithm=serialization.NoEncryption()
    )
    return pub_pem, priv_pem
```

#### Performance trade-off

| Key Size | Key Generation | RSA-OAEP Encrypt | RSA-OAEP Decrypt |
|---|---|---|---|
| 2048-bit | ~50ms | ~1ms | ~5ms |
| 4096-bit | ~400ms | ~2ms | ~20ms |

Key generation is ~8× slower, but it only happens once at registration. The per-operation
encrypt/decrypt cost (wrapping/unwrapping the AES key) is negligible — 2ms vs 20ms on
a laptop CPU.

## Part 2 — TLS Enforcement Warning

Running MedVault over plain HTTP in production would expose everything — not because
the data is decrypted server-side (it isn't) but because the JWT tokens in
`Authorization` headers would be interceptable, allowing session hijacking.

Added a startup warning:

```python
# server/server.py — startup block

import os

BEHIND_TLS_PROXY = os.environ.get("BEHIND_TLS_PROXY", "").lower() in ("1", "true", "yes")
FLASK_ENV        = os.environ.get("FLASK_ENV", "production")

if FLASK_ENV != "development" and not BEHIND_TLS_PROXY:
    import warnings
    warnings.warn(
        "\n"
        "⚠ WARNING: MedVault is running without TLS.\n"
        "   JWT tokens transmitted over plain HTTP are interceptable.\n"
        "   Set BEHIND_TLS_PROXY=true if running behind nginx/Caddy/Cloudflare.\n"
        "   Set FLASK_ENV=development to suppress this warning in local dev.\n",
        UserWarning, stacklevel=2
    )

# HSTS header — only set when TLS is confirmed
@app.after_request
def security_headers(response):
    response.headers["X-Content-Type-Options"] = "nosniff"
    response.headers["X-Frame-Options"]        = "DENY"
    response.headers["X-XSS-Protection"]       = "1; mode=block"
    if BEHIND_TLS_PROXY:
        response.headers["Strict-Transport-Security"] = "max-age=31536000; includeSubDomains"
    # Note: HSTS on plain HTTP causes browser lockout — only set behind TLS
    return response
```

The HSTS header is conditionally set because HSTS on a plain-HTTP server causes browsers
to permanently refuse to connect over HTTP — which bricks the site until the HSTS
cache entry expires (up to a year for `max-age=31536000`).

## Part 3 — Committed Secrets Prevention

Added both `api_key.txt` and `jwt_secret.txt` to `.gitignore` and added a startup
guard that raises `RuntimeError` if either file exists in a non-dev environment:

```python
# server/server.py — startup

API_KEY_FILE     = Path("server/api_key.txt")
JWT_SECRET_FILE  = Path("server/jwt_secret.txt")

if FLASK_ENV != "development":
    for secret_file in [API_KEY_FILE, JWT_SECRET_FILE]:
        if secret_file.exists():
            raise RuntimeError(
                f"Secret file {secret_file} found in non-development environment. "
                f"Use environment variables instead: "
                f"SERVER_API_KEY, JWT_SECRET"
            )
```

This makes accidental production deployments with committed secrets impossible —
the server refuses to start.

## Part 4 — Security Remediation Retrospective

Over the past 10 days, 25 security issues were addressed across 4 severity levels:

| Severity | Issues Fixed | Examples |
|---|---|---|
| **Critical** | 4 | Committed secrets, plaintext key storage, JWT==API key, note auth bypass |
| **High** | 7 | IDOR, legacy SHA-256 hashing, in-memory blocklist/OTP, file upload, status validation |
| **Medium** | 8 | No TLS warning, RSA 2048→4096, CORS wildcard, rate limiter persistence |
| **Low** | 6 | Missing security headers, log injection, error information leakage |

Key pattern observed: most of the vulnerabilities were **in-memory state issues** —
things that worked correctly in a single-server, no-restart development environment
but silently broke in production (rate limiter, token blocklist, OTP store). The fix
pattern was always the same: persist the state to a file or database, reload on startup,
discard expired entries.

The second most common pattern was **missing authorization checks** — endpoints that
validated *who* the caller was (via JWT) but didn't validate *whether* they were
allowed to access the specific resource they requested (IDOR).

## Questions I Still Have

- At 4096-bit, key generation takes ~400ms. For a high-traffic registration endpoint, should key generation be moved to a background task and the user notified when it's ready?
- The startup guard checks for secret files but doesn't verify that the env var alternatives are actually set. A server could start with `FLASK_ENV=production`, no secret files, and no env vars — defaulting to an empty/insecure key. Should there be a positive validation that the secrets are non-empty?
- Is there a clean way to test the HSTS conditional behaviour in unit tests without actually changing the environment?
